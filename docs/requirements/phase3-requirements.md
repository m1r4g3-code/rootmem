# Phase 3 Requirements & Constraints — Procedural Memory, Failure→Lesson Distillation & SKILL.md

## Exit criterion

> Given a namespace that receives, via `ingest_session`: **(i)** two separate sessions (distinct `session_id`s), each an ordered 3-step sequence describing, in different words, the same underlying procedure (e.g. "a test fails with error X" → "the root cause is Y" → "the fix is Z, tests pass"), each submitted with `session_outcome="success"`; **(ii)** one more session, a distinct failed attempt at a related task, submitted with `session_outcome="failure"`, whose steps name one clear proximate cause; **(iii)** three restatements of an unrelated fact (Phase 2's own corroboration scenario, reused to prove coexistence) and enough total episodes to cross `consolidation_episode_threshold` — the system must, end-to-end via MCP:
>
> **(a)** after the threshold is crossed (or an explicit `consolidate(force=True)` call), a consolidation pass groups episodes by `(source_session_id, session_outcome)`, embeds each qualifying session's trace summary, clusters the two successful traces together via reused `cluster_by_similarity` at `procedural_session_similarity_threshold`, and distills them (since `procedural_min_recurrence=2` is met) into exactly one `procedural_memories` row with `kind="skill"`, a name/description satisfying the SKILL.md spec's own constraints, and `procedural_memory_provenance` links back to all 6 source episodes — provable via `get_skill`;
> **(b)** the single failed session (meeting `lesson_min_recurrence=1`, no repetition required) is separately distilled into a `procedural_memories` row with `kind="lesson"` naming the proximate cause and what to avoid — provable via `get_skill`;
> **(c)** the same `consolidation_runs` row records `procedures_distilled=1`, `lessons_distilled=1`, alongside Phase 2's own `facts_distilled>=1` from the reused corroboration ingredient — proving procedural/lesson distillation runs inside the same sleep cycle as episodic→semantic distillation, not a separate, parallel subsystem;
> **(d)** a simulated later session — with no prior knowledge of the skill's exact name, using a query sharing no words with it — calls `find_skill` with only a natural-language description of a fresh instance of the same task, and gets the distilled skill ranked above the unrelated lesson, proving semantic retrieval discriminates on real content, not name- or keyword-matching (`find_skill` searches only `procedural_memories`, so it structurally cannot surface raw episodic memories at all — that exclusion is itself part of the proof: skills/lessons and episodes are deliberately different search domains, `find_skill` vs. `search`);
> **(e)** that session then calls `get_skill(name)` with the name `find_skill` returned, receives literal SKILL.md-conformant markdown text (valid frontmatter + body), and correctly follows its documented steps via ordinary subsequent MCP tool calls — the "applies it correctly" proof, deliberately scoped to what's observable through MCP tool calls alone: **no benchmark harness, no reference coding agent, no real SWE-bench/Terminal-Bench task run** (the user's explicit scope decision for this phase — see non-goals below and ADR 0021).

This is the single pass/fail gate for tagging `v0.3.0-phase3`, validated by one automated integration test (`tests/integration/test_phase3_exit_criterion.py`) and one manual dogfooding pass recorded in `scripts/manual_phase3_check.md` — the same dual automated+manual sign-off ritual Phase 0/1/2 used.

## Functional requirements

- FR1: `ingest_session` gains a `session_outcome: Literal["success", "failure"] | None = None` parameter — a cheap, optional, agent-supplied signal, mirroring Phase 2's `importance_flag` precedent exactly. `remember` does NOT gain this parameter (it has no session/sequence concept).
- FR2: `consolidation/distill.py`'s `run_consolidation` gains a procedural-distillation stage, run in the same pass as (and after) Phase 2's existing episodic→semantic stage: group the current batch's already-fetched episodes by `(namespace, source_session_id, session_outcome)`, filtering to sessions with at least `procedural_min_session_length` episodes and a non-null `session_outcome`; embed one trace-summary text per qualifying session; cluster success-outcome session traces via the reused `cluster_by_similarity` at `procedural_session_similarity_threshold`; for each cluster meeting `procedural_min_recurrence`, and for each individual failure-outcome session meeting `lesson_min_recurrence`, call `ProceduralDistillationProvider.distill_procedure` and persist the result via `ProceduralMemoryRepository.create`, linking `procedural_memory_provenance` to every source episode.
- FR3: A new `ProceduralMemoryRepository` Protocol (`storage/procedural_protocols.py`) stores distilled skills/lessons: `create`, `get_by_name`, `search_hybrid` (text + vector, mirroring `MemoryRepository.search_hybrid`'s existing shape), `link_provenance`, `get_provenance`, `supersede`. Two implementations (`PostgresProceduralMemoryRepository`, `InMemoryProceduralMemoryRepository`), contract-tested identically to every existing Protocol in this codebase.
- FR4: A new `ProceduralDistillationProvider` Protocol (`consolidation/procedural_protocols.py`) — `distill_procedure(traces: list[list[str]], context) -> SkillDraft` (`name`/`description`/`body_markdown`). Real: `AnthropicProceduralDistillationProvider` (Haiku-tier, tool-calling). Fake: `ScriptedProceduralDistillationProvider`.
- FR5: A new pure module `consolidation/skill_format.py` validates and renders SKILL.md-conformant content: `validate_skill_name` (lowercase, hyphens only, ≤`skill_name_max_length` characters), `validate_skill_description` (≤`skill_description_max_length` characters), `render_skill_markdown` (YAML frontmatter + body, agentskills.io-conformant).
- FR6: A new pure module `consolidation/procedural_clustering.py` — `cosine_similarity(a, b) -> float`, `group_session_traces(episodes) -> list[SessionTrace]`, and construction of the `(id, id, similarity)` pairs `cluster_by_similarity` (reused unmodified from `consolidation/clustering.py`) expects, built from trace-summary embeddings rather than raw episode embeddings.
- FR7: Two new MCP tools: `find_skill(query, namespace, kind: Literal["skill","lesson","all"]="all", limit=10)` — hybrid search over `procedural_memories`, returning ranked results; `get_skill(name, namespace)` — returns literal SKILL.md-conformant markdown text for one named, active procedural memory (or `found: false` if none exists).
- FR8: `ConsolidationRun`/`consolidation_runs` gain `procedures_distilled: int = 0`, `lessons_distilled: int = 0`, populated by the same `complete_run` call Phase 2's `facts_distilled` already uses (extended with two new parameters, not new methods).
- FR9: A name collision on re-distillation (a new skill/lesson would take an already-active name in the same namespace) supersedes the old `procedural_memories` row (`supersedes`/`superseded_by`, mirroring `relations`' existing soft-supersede mechanics) rather than overwriting it in place or erroring.

## Non-functional requirements

- NFR1 (write-path latency unaffected): `ingest_session`'s latency budget is unchanged — `session_outcome` is a passthrough field with zero additional processing at write time; all procedural distillation work happens in the batch consolidation pass, never inline.
- NFR2 (no new worker infrastructure): procedural distillation reuses the exact trigger/execution model Phase 2 already built (`consolidation/trigger.py`'s `should_consolidate`, the inline `asyncio.create_task` auto-trigger, the explicit `consolidate` tool/CLI) — no new queue/worker service, no second trigger (ADR 0020).
- NFR3 (no new heavy ML dependency): session-trace cosine similarity is pure Python (a handful of floats) — no `numpy`/`scikit-learn`-class dependency is added to `pyproject.toml`, extending ADR 0015's discipline.
- NFR4 (type safety): `mypy --strict` continues to pass with zero errors, zero suppressions, across all new modules.
- NFR5 (testability): all new business logic (session-trace grouping, cosine similarity, SKILL.md validation/rendering) is a pure function, unit-testable with zero I/O, zero external-API, zero Docker dependency.
- NFR6 (schema discipline): `procedural_memories` follows `memories`/`relations`' existing conventions — `DOUBLE PRECISION`/`VECTOR(1024)` typing consistent with Phase 1's embedding column, `namespace` scoping throughout, never a hard `DELETE` (soft-delete columns present, supersede-not-overwrite on name collision).
- NFR7 (cost control): real-API integration tests exercising `AnthropicProceduralDistillationProvider` run in the existing sparse, secret-gated `integration-external` CI job — not a new one.
- NFR8 (config): all new tunables load via the existing `pydantic-settings` `Settings` class, fail-fast at startup, documented as provisional defaults in `docs/math-spec/phase3-math-spec.md`.
- NFR9 (layer isolation): `consolidation/` never imports `anthropic` directly outside `anthropic_procedural_distillation_provider.py` — a Protocol-based port, consistent with ADR 0009's precedent.
- NFR10 (SKILL.md conformance): every `procedural_memories` row's `name`/`description` passes `skill_format.validate_skill_name`/`validate_skill_description` before being persisted — a malformed draft from the distillation provider is rejected (logged, degraded, the cluster is skipped this pass) rather than stored non-conformant, mirroring `consolidation/distill.py`'s existing `DistillationError` graceful-degradation pattern for Phase 2's own distillation calls.

## Explicit non-goals for Phase 3

A benchmark harness, a reference coding agent, and real SWE-bench Verified/Terminal-Bench task runs (the Build Reference's literal exit criterion for this phase — explicitly rejected per ADR 0021 in favor of a scoped-down MCP-native proof, the user's own confirmed decision; named revisit trigger: a real harness becoming available/needed in Phase 4+); literal SKILL.md folder writes to any filesystem location (rejected per ADR 0018 — ROOTMEM produces conformant content, never installs it); inferring `session_outcome` from `relation_feedback` or any other implicit signal (rejected per ADR 0019); k-means/HDBSCAN or any `scikit-learn`/`numpy`-class ML dependency (session-trace similarity stays pure Python, per NFR3); a new worker/queue service (procedural distillation reuses ADR 0012's existing execution model, per ADR 0020 and NFR2); `remember` gaining a `session_outcome` parameter (scoped to `ingest_session` only — see FR1); versioned skill "update" semantics beyond simple name-collision supersession (FR9); a skill "usage/effectiveness" tracking mechanism (an `applied_count` or measured-success-rate field) — Phase 4's trust/provenance-scoring territory, not this phase's; a Bayesian belief/confidence field on `procedural_memories` (a distilled skill/lesson is not a contestable factual claim the way a `relations` row is); decay/forgetting curves, trust/provenance scoring, the multi-factor retrieval-ranking formula, and the tamper-evident audit log (Phase 4, unchanged); cross-instance identity continuity and REST API/remote transport (Phase 4/5+, unchanged). These are non-goals, not deferred requirements to sneak in early.

**A known, named limitation, not a bug**: a session whose steps are ingested across two separate consolidation passes (straddling `consolidation_batch_size`) is not grouped as one trace — each pass only clusters within its own currently-unconsolidated batch, the same class of limitation Phase 2's retro named for episodic→semantic clustering's batch scoping. The exit criterion controls its own scenario timing to avoid tripping this; carried forward as an open item for Phase 4 to revisit only if real usage shows it matters.

## Traceability to charter global standards

| Charter standard | How Phase 3 satisfies it |
|---|---|
| Type safety everywhere | `mypy --strict` CI gate, extended to all new modules |
| Schema versioning from day one | `procedural_memories`/`procedural_memory_provenance` follow `memories`/`relations`' existing conventions |
| Every write is attributable | Every `procedural_memories` row carries `procedural_memory_provenance` links back to every source episode it was distilled from |
| Every destructive operation is soft | Name-collision re-distillation supersedes (`supersedes`/`superseded_by`), never overwrites or deletes; soft-delete columns present |
| Idempotency by default | `consolidate` with an unmet trigger and `force=False` remains a clean no-op (unchanged from Phase 2); a re-run distilling an identical cluster supersedes cleanly rather than duplicating |
| Observability from first commit | Procedural/lesson distillation logged via the existing `observability/metrics.py` pattern; degraded/rejected drafts logged per NFR10 |
| No unbounded LLM calls | Procedural distillation runs once per qualifying session-trace cluster per consolidation pass, bounded by the same `consolidation_batch_size` Phase 2 already bounds episodic distillation with |
| Config over code | All new tunables in `pydantic-settings`, per NFR8 |
| Everything testable in isolation | `ProceduralMemoryRepository`, `ProceduralDistillationProvider` Protocols, each with a fake, per NFR5 |
