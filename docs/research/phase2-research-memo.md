# Phase 2 Research Memo — Consolidation, Salience & Bayesian Belief

**Phase:** 2 — Consolidation, Salience & Bayesian Belief
**Date:** 2026-09-18
**Inputs:** ROOTMEM Research Report, ROOTMEM Build Reference (both re-provided by the user for this phase specifically, since neither document was ever saved into the repo after Phase 0 — only cited); `docs/adr/0008`, `docs/math-spec/phase1-math-spec.md`, `docs/retro/phase1-retro.md`; fresh external research conducted 2026-09 for this memo.

## Scope of this memo

Phase 1 shipped a deliberately deterministic contradiction rule (ADR 0008) and left `retrieval/ranking.py`'s `γ·salience` and the consolidation trigger as unfilled symbolic placeholders, both explicitly assigned to Phase 2. This memo covers three things: (1) re-evaluating the Build Reference's original Phase 2 candidate formulas against fresh 2026 research, the same re-evaluation discipline Phase 1 applied to Phase 0's graph-store and embedding-model candidates; (2) two real gaps in Phase 1's own shipped code, found while reading it (not just its docs) during this phase's planning; (3) the scope boundary the user set explicitly for this phase.

## Re-evaluating the Build Reference's Phase 2 candidates

The Build Reference (§5, steps 8-12) proposed: a consolidation trigger (N unprocessed episodes OR time window T), a linear salience formula (`S = w1·novelty + w2·user_flagged_importance + w3·repetition_count + w4·task_relevance`), k-means/HDBSCAN clustering for episodic→semantic distillation, and (bundled into the same phase) episodic→procedural and failure→lesson distillation. Fresh research this cycle changes three of these:

**Consolidation execution has no home in this project's actual infrastructure.** The Build Reference recommends Celery/RQ/n8n for background jobs — reasonable general advice, but ROOTMEM has never run a persistent worker process anywhere. The MCP server is a stdio subprocess launched per client session (see `src/rootmem/integration/mcp/server.py`); every prior infrastructure decision in this project has deliberately avoided adding a new service specifically because of this dev machine's Docker/WSL2 constraints (ADR 0006 rejected a dedicated graph engine, ADR 0010 rejected an HTTP webhook listener, both explicitly on this basis). Adding Celery/RQ now would be the first time this project takes on a new long-running service, for a job that a synchronous on-demand tool call plus one background `asyncio.create_task` — a technique this codebase already proved out for an unrelated problem (see below) — can handle without it. See ADR 0012.

**k-means/HDBSCAN would be this project's first ML-library dependency.** No `numpy`/`scikit-learn`-class dependency exists anywhere in `pyproject.toml` today. pgvector's cosine-distance operator (`<=>`) is already in production use (Phase 1's `search_semantic`/`search_hybrid`); a bounded self-join over it, combined with union-find (a well-known ~30-line pure-Python algorithm, no library needed), clusters near-duplicate episodes at the scale this phase's exit criterion and any realistic near-term usage actually need. `scripts/spike_similarity_clustering.py` (Prototype stage, run before finalizing ADR 0015) validates this holds up on a small synthetic mixed set before committing. See ADR 0015.

**Real production belief-revision systems corroborate a Bayesian approach, but with implementation choices the Build Reference doesn't specify.** The Build Reference names "real Bayesian contradiction math" as Phase 2's job (via ADR 0008's own citation) without giving a concrete formula. Fresh research into 2026 production/research systems (arXiv:2606.22030, "Belief-Based Agent Memory"; arXiv:2603.17244, "Formal Belief Revision Semantics for Versioned Memory Architectures") surfaced a converging pattern: treat a fact's confidence as a Bayesian belief, where new corroborating or conflicting evidence updates a posterior weighted by per-source reliability, rather than a flat most-recent-wins rule. One system design pattern found — computing confidence dynamically at read-time from a raw evidence-event log, rather than storing it as a field — was considered and explicitly not adopted (see ADR 0013's rationale: Beta-Bernoulli conjugacy makes a small, cheap, *stored* sufficient statistic equivalent in information content to replaying the full event log on every read, at a fraction of the read cost `search`/`related` already depend on). AGM-compliant belief revision theory (Success, Consistency, minimal-change/Relevance postulates) is cited in `docs/math-spec/phase2-math-spec.md` as the formal framework the design is checked against, not implemented in full generality.

**Zep/Graphiti remains the most sophisticated production consolidation mechanism**, per both the original Research Report and fresh confirmation this cycle: bi-temporal validity windows with invalidation-not-deletion on contradiction. ROOTMEM's Phase 1 graph already implements the equivalent mechanism structurally (`valid_to`/`supersedes`/`superseded_by`) — Phase 2's job is to make the *decision* of when to invalidate probabilistic rather than deterministic, not to change the bi-temporal storage shape itself. One real-world caveat surfaced worth carrying forward: Zep's own reported production experience shows immediate post-ingestion retrieval sometimes failing until background graph processing completes — a direct precedent for why this phase's exit criterion tests the consolidation trigger explicitly rather than assuming it always completes synchronously before the next read.

## Two real gaps found in Phase 1's shipped code (not just its docs)

Both confirmed by direct file read during this phase's planning, not inferred from documentation:

1. **ADR 0008 and `docs/math-spec/phase1-math-spec.md` both state the deterministic rule is "isolated as a pure function (`extraction/contradiction.py`)". That file does not exist.** The rule is duplicated inline inside `PostgresGraphRepository.create_relation` and `InMemoryGraphRepository.create_relation`. Phase 2's Bayesian rewrite is the first real opportunity to close this gap — the new `resolve_contradiction`/`apply_feedback` functions are written once, in that file, and called by both implementations, rather than duplicating Bayesian math twice the way the deterministic rule was.
2. **`create_relation`'s contradiction query never compares `object_entity_id`/`object_literal`.** `src/rootmem/storage/postgres/graph_repository.py:142-152` (confirmed by direct read) matches purely on `(namespace, subject_entity_id, predicate)` with `valid_to IS NULL`. Restating an identical fact ("Alice works at Acme Corp" said twice, in different words) is indistinguishable, at the query level, from a genuine contradiction — it silently supersedes the first relation with the second. This is exactly the failure mode real Bayesian corroboration is supposed to fix: an agreeing restatement should raise confidence in the existing relation, not replace it with an indistinguishable copy. This phase's exit criterion is written specifically to prove this gap is closed (see `docs/requirements/phase2-requirements.md`).

## What this phase's research does NOT yet resolve

- **Salience weight tuning.** The four-term formula's weights (`w1..w4`) ship as reasonable defaults (`task_relevance` weighted to zero — no task-modeling primitive exists anywhere in this codebase to compute it from), not empirically tuned. The Build Reference itself says these should be "tuned empirically... against retrieval-quality outcomes" — that requires a real usage corpus and an eval harness this project doesn't have yet. Carried forward to Phase 4, alongside the ranking formula's other untuned weights (`hybrid_search_weight_text`/`hybrid_search_weight_vector`, already provisional since Phase 1).
- **Bayesian prior strength and source-reliability weights** (`bayesian_prior_strength`, `bayesian_source_reliability_*`) are likewise shipped as documented, reasonable defaults, not calibrated against real retrieval-outcome data — there is no such data until the `feedback` tool this phase adds has been used in practice. This is the same "no signal yet to design against" position ADR 0008 itself took toward attempting Bayesian math in Phase 1.
- **Whether `consolidation_episode_threshold`/`consolidation_time_window_hours` are the right trigger shape** at real usage scale (hundreds to thousands of memories per namespace) is unknown — Phase 2 ships one, documented, testable default; tuning it is explicitly deferred until real namespaces exist to observe.
- **Episodic→procedural distillation and failure→lesson distillation**, per the user's explicit scope decision for this phase, move to Phase 3 bundled with the SKILL.md format work they depend on — building a procedural-memory output format before that format is formally speced would be throwaway work Phase 3 would redo anyway.

## Open questions carried forward to Phase 3's research memo

- Whether the Beta-Bernoulli belief model, once exercised against real `feedback` calls, produces confidence movement that actually correlates with retrieval quality — the concrete calibration question ADR 0008 originally deferred to "once Phase 2 exists."
- Whether `consolidation/distill.py`'s clustering-then-LLM-abstraction pattern, once it has real episodic data to run against, generalizes cleanly to episodic→procedural distillation, or whether procedural memory needs a materially different clustering signal (successful vs. failed trajectories, not just semantic similarity).
- Whether the similarity-threshold union-find approach (ADR 0015) holds up at real namespace scale, or whether the revisit trigger it names (cluster quality degrading, or namespaces large enough that the pgvector self-join becomes the bottleneck) fires before Phase 4.
