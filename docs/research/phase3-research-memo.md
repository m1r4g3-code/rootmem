# Phase 3 Research Memo — Procedural Memory, Failure→Lesson Distillation & SKILL.md

**Phase:** 3 — Procedural Memory, Failure→Lesson Distillation & SKILL.md
**Date:** 2026-09-18
**Inputs:** ROOTMEM Research Report, ROOTMEM Build Reference (both previously provided by the user, cited from Phase 0/2 memos); `docs/retro/phase2-retro.md`, `docs/research/phase2-research-memo.md`, `docs/adr/0006` (the "different aggregate → different Protocol" test), `docs/adr/0009` (Protocol-per-provider pattern), `docs/adr/0012`/`0014`/`0015`/`0016` (infra-minimalism precedents this phase reuses); a dedicated repo-wide Explore pass across every ADR/research-memo/requirements/retro file for existing Phase 3 forward-references; fresh external research conducted 2026-09 for this memo.

## Scope of this memo

Phase 2's own retro and research memo hand Phase 3 exactly two things, explicitly, by the user's own scope decision: episodic→procedural distillation, failure→lesson distillation, and the SKILL.md format they depend on. A dedicated Explore pass across the entire repo (every ADR, research memo, requirements doc, retro, and the master plan file) confirmed there is **zero existing mechanical design** for any of this — every prior reference is scope-naming only ("Phase 3 owns X"), never a schema, clustering signal, or Protocol sketch. This memo is that first mechanical design pass, plus the fresh external research needed to ground it.

## SKILL.md is now a real, adoptable spec — not something to invent

At the time Phase 0/1/2's docs named "SKILL.md format" as forward-looking scope, no formal external standard existed to point at. That changed in December 2025: **agentskills.io published an open SKILL.md standard**, now the reference this phase adopts rather than designing from scratch. The spec is deliberately minimal: a folder per skill, a `SKILL.md` file inside it with YAML frontmatter carrying exactly two required fields — `name` (lowercase, hyphens only, ≤64 characters, must equal the folder name) and `description` (≤1024 characters, stating both *what* the skill does and *when* to use it) — plus free-form markdown body content, and optional `scripts/`/`references/`/`assets/` subdirectories loaded via progressive disclosure. Adopting this published spec directly (rather than inventing a ROOTMEM-specific format) means Phase 3's distilled output is portable to any client that already understands SKILL.md, not a bespoke format only ROOTMEM's own tools can read.

**A concrete adoption constraint this format's own definition creates**: SKILL.md is fundamentally a *filesystem* artifact — a folder a coding agent's tool reads from disk. ROOTMEM is an MCP stdio server, launched as a subprocess per client session, with no general filesystem-write channel to wherever a client's own skills directory happens to live (this varies by client and host machine, and guessing a path would be exactly the kind of unprincipled, unverifiable behavior the charter's engineering standards exist to prevent). This phase's design therefore treats **producing valid SKILL.md-conformant content, handed back over MCP,** as the boundary of ROOTMEM's responsibility — "installing" it into a real skills directory is the calling agent's or human's job, a clean division of labor rather than a scope gap. See ADR 0018.

## Procedural memory's clustering signal: session traces, not raw episode similarity

The central open question Phase 2's retro named (`docs/research/phase2-research-memo.md:40`): does `consolidation/distill.py`'s existing clustering-then-LLM-abstraction pattern generalize to episodic→procedural distillation, or does procedural memory need a materially different signal?

Direct examination of the shipped schema resolves this cleanly. `MemoryRecord`/`NewMemory` (`storage/models.py`) already carry `source_session_id`, populated whenever `ingest_session` is called with a `session_id` — real structure, already shipped, unexploited by any consolidation logic today. Phase 2's semantic distillation clusters *individual* episodes by raw content similarity, because a fact is a single, flat claim. A *procedure* is not a single claim — it is an ordered sequence of steps that, taken together, led to an outcome. Clustering at the individual-episode level would merge disconnected steps of unrelated attempts purely because they happen to share vocabulary; the unit of comparison has to be the *session*, not the episode. This memo therefore resolves the open question: **the pattern partially generalizes (union-find over cosine similarity is reused verbatim, per `docs/research/phase2-research-memo.md`'s original infra-minimalism argument for it), but the input it operates over must change** — from raw episode embeddings to one embedding per qualifying session trace (a summary joining that session's ordered steps into one text, embedded once via the already-injected `EmbeddingProvider`). Two structurally-repeated, differently-worded successful sessions then cluster as one candidate skill; a single successful session with no repeat is not yet a pattern, and a single failed session is retained on its own terms as a candidate lesson. See ADR 0017.

## Failure signal: an explicit flag, not inference from existing feedback machinery

Phase 2 shipped `feedback`/`relation_feedback` (ADR 0014) as an explicit, agent-reported signal about whether a *fact* was correct — deliberately not inferred from `search`/`related` read access, on the grounds that a read is not validation. The same discipline applies here by direct extension, not by analogy: "was this fact correct" and "did this task attempt succeed" are different aggregates answering different questions, and `relation_feedback` rows are keyed to a `relation_id`, not a session. Reusing it to infer session-level failure would repeat the exact category error ADR 0014 already rejected once. Fresh research confirms this is the right default posture for a system with no real usage volume yet: without observed data correlating fact-level contradiction feedback with session-level task failure, building an inference layer would be speculative machinery calibrated against nothing. Phase 3 instead adds one new, cheap, explicit, optional flag — `session_outcome: "success" | "failure"` — mirroring `importance_flag`'s exact precedent from Phase 2 (an agent-supplied signal at `ingest_session` time, no new capture concept, no inference). See ADR 0019.

## Re-evaluating the Build Reference's Phase 3 candidates

The Build Reference's literal Phase 3 exit criterion calls for a measurable lift (3-5+ points) on SWE-bench Verified or Terminal-Bench for a reference coding agent using ROOTMEM's memory versus without it. Fresh consideration this cycle, and an explicit choice put to the user (see `docs/requirements/phase3-requirements.md`'s non-goals), finds this disproportionate to this phase's actual deliverable: a real benchmark lift requires a benchmark harness, a reference coding agent implementation, and real, repeated, costly coding-task runs — an entirely new class of infrastructure this project has never built, for a claim ("our memory makes agents measurably better at real coding tasks") that is a Phase 4+-scale research question once procedural memory itself exists to evaluate. Every phase to date has scoped its own exit criterion down from the source material's most ambitious framing for exactly this kind of infra-cost/architectural-fit reason (Phase 0: no graph engine; Phase 1: deterministic not Bayesian yet; Phase 2: procedural distillation itself deferred out). Given this precedent, the user was asked directly and chose the same pattern for Phase 3: prove the induction → storage → retrieval → application mechanism works end-to-end via direct, cheap MCP tool calls, with no benchmark harness. The named revisit trigger (recorded in ADR 0021): a real benchmark harness becoming available, or becoming load-bearing to a stakeholder claim, in Phase 4 or later.

## What this phase's research does NOT yet resolve

- **Whether `procedural_session_similarity_threshold=0.80` (carried over from Phase 2's `distillation_similarity_threshold` default) is the right number for session-trace-level embeddings**, as opposed to individual-episode embeddings it was originally validated for. `scripts/spike_session_trace_clustering.py` (Prototype stage, run before finalizing ADR 0017) validates this empirically against real `voyage-4` embeddings before being locked in, mirroring Phase 2's own spike-before-ADR discipline for its threshold.
- **Whether `procedural_min_recurrence=2`/`lesson_min_recurrence=1` are the right asymmetric bar.** The asymmetry itself (skills need repetition, a single failure is already worth recording) is a considered design choice, not an empirically-derived number — there is no real usage data yet to tune either constant against.
- **Whether a coding agent, given a retrieved SKILL.md-shaped artifact via `get_skill`, reliably follows it correctly on tasks materially different from the exit criterion's own scenario** — this phase's exit criterion proves the mechanism (retrieval discriminates correctly, the content is well-formed, one concrete follow-through succeeds), not generalized real-world efficacy at scale. That claim is exactly what a real benchmark (deferred per ADR 0021) would be needed to support.
- **The known batch-scoping limitation**: a session whose steps straddle two separate consolidation passes (crossing `consolidation_batch_size`) is not grouped as one trace, since each pass only clusters within its own currently-unconsolidated batch — the same class of limitation Phase 2's retro named for its own episodic→semantic clustering. Carried forward as an open item for Phase 4 to revisit only if real usage shows it matters.

## Open questions carried forward to Phase 4's research memo

- Whether a "skill effectiveness" or "applied successfully N times" tracking mechanism belongs to procedural memory itself or to Phase 4's trust/provenance-scoring territory — this phase deliberately ships no such mechanism (see non-goals), treating it as a trust-scoring concern rather than a distillation concern.
- Whether real usage ever produces a session long/complex enough to trip the batch-scoping limitation named above.
- Whether `bayesian`-style belief tracking (Phase 2's mechanism for facts) has any analog worth applying to procedural memories' own confidence — this phase gives `procedural_memories` no belief/confidence field at all, since a distilled skill/lesson is not itself a contestable factual claim the way a relation is; revisit only if a real need for skill versioning-with-confidence emerges.
