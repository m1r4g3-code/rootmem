# Phase 1 Research Memo — Semantic Graph, Vector Retrieval & Extraction

**Phase:** 1 — Semantic Graph, Vector Retrieval & Extraction
**Date:** 2026-09-16
**Inputs:** ROOTMEM Research Report, ROOTMEM Build Reference (both provided at project kickoff, same as Phase 0); Phase 0's own docs (`docs/adr/0001`, `docs/research/phase0-research-memo.md`, `docs/requirements/phase0-requirements.md`, `docs/math-spec/phase0-math-spec.md`, `docs/retro/phase0-retro.md`) — there is no separate standalone multi-phase charter file, so Phase 1's scope had to be reconstructed from forward-references scattered across those documents; fresh external research conducted 2026-09 for this memo specifically.

## Scope of this memo

Phase 0 shipped a bare MCP server with no semantic search, no graph, and no LLM calls — every memory was explicit, agent-authored content. ADR 0001 named "Phase 1 kickoff" as "the forced re-evaluation point, not an indefinite deferral" for the graph-store decision it punted. This memo is that re-evaluation, plus the embedding-model decision Phase 0's schema comments and NFR6 explicitly left open. It also covers the two new pipeline layers (`capture/`, `extraction/`) whose module stubs already commit to rough scope ("session-lifecycle hooks, webhook capture, and batch import"; "LLM-based fact/event/entity/relation extraction ... plus contradiction detection").

## Re-evaluating ADR 0001: the graph store decision

ADR 0001 deferred choosing between "KuzuDB or Postgres+AGE" because Phase 0 had no bi-temporal edge model to test either against. That model now exists (this phase builds it), so the deferral's own condition for revisiting has been met. Fresh research this cycle found that **both of Phase 0's originally-named candidates have separately become unsafe choices** since that ADR was written:

- **KuzuDB was archived in October 2025**, after Apple acquired the company behind it. Maintenance passed to community forks (LadybugDB, Bighorn) with no corporate backing and real abandonment risk. Starting a new production dependency on an orphaned project would be a mistake regardless of its prior technical merits.
- **Apache AGE has no official Windows support** — its documentation assumes Linux/WSL. A third-party fork (`ShanGor/apache-age-windows`) publishes precompiled Windows binaries bundling AGE+pgvector+Postgres 17, but that fork is exactly the same risk class as pgvector's own missing-Windows-binary problem that already cost real development time in Phase 0 (see `scripts/manual_recall_check.md`'s blocker note).
- **ArcadeDB** (Apache 2.0, ArcadeData org, positioned as the leading open-source Neo4j alternative in 2026) is a genuine third option neither Phase 0 document named. Its `arcadedb-embedded` Python package publishes real PyPI wheels for Windows x86_64 (also Linux x86_64/ARM64, macOS Apple Silicon), runs in-process with no separate server, and implements OpenCypher 25 at a 97.8% TCK pass rate. It is the only graph-database candidate with a demonstrated native-Windows install path. Its cost: it is a JVM library under a Python wrapper (bundles its own Java 25 runtime) — a class of runtime (JVM startup, GC behavior, cross-language binding) nothing else in this stack has exercised.

**Decision (see ADR 0006, which formally supersedes ADR 0001): model the bi-temporal semantic graph as plain Postgres tables** (`entities`, `relations`, `memory_entities`), not a dedicated graph engine. The reasoning that tips this, beyond ArcadeDB's own JVM-dependency cost: Phase 0's CI already runs Postgres+pgvector successfully on GitHub Actions' `ubuntu-latest` runners via Docker, every time, with no WSL2/hypervisor exposure at all. The native-Windows pressure that shaped so much of Phase 0's actual development experience is a property of one physical developer laptop's local inner loop — it does not apply to CI or to any real production deployment target. Once Postgres is already running everywhere that actually matters, two more tables in the same database cost zero new infrastructure and zero new Windows-compatibility surface, versus a graph engine whose only virtue *for this specific problem* was solving a Windows-install pain point that doesn't generalize past local dev. Recursive CTEs handle the traversal depth Phase 1's exit criterion needs (1-2 hops); ADR 0006 names a concrete revisit trigger (query-plan cost or hop-depth demand) rather than leaving this as another indefinite "not yet."

This is not a second silent deferral. A timeboxed spike (`scripts/spike_arcadedb_embedded.py`) actually installs and exercises `arcadedb-embedded` on this Windows Python 3.13 box before ADR 0006 is finalized, and its findings are banked regardless of which way the decision goes, specifically so a future phase revisiting this question inherits real data instead of the same secondhand research this memo had to start from.

## Re-evaluating the embedding model

Phase 0's research memo assumed the Voyage `voyage-3` family (voyage-3-lite=512 dims, voyage-3=1024, voyage-3-large=configurable) — the dimension-to-tier coupling that justified leaving `content_embedding` unconstrained rather than guessing. That family has since been **superseded by voyage-4** (voyage-4-lite/voyage-4/voyage-4-large), which decouples dimension entirely from tier: every tier supports Matryoshka Representation Learning truncation to 256/512/1024/2048 dimensions. Pricing: voyage-4-lite $0.02/M tokens, voyage-4 $0.06/M, voyage-4-large $0.12/M tokens; all with a 32K-token context window and 200M free tokens per account.

**Decision (see ADR 0007): `voyage-4` at 1024 dimensions, HNSW index with `vector_cosine_ops`.** Middle tier over `-lite` (this system isn't bulk-corpus-shaped — it's a personal/small-team agent memory store, not high-throughput indexing) and over `-large` (no benchmark of ours justifies paying 2x for an unproven marginal quality gain — directly following Phase 0's own warning against trusting saturated/self-reported benchmarks, §"Benchmarks are saturated/self-reported"). 1024 dimensions sits where pgvector's HNSW index performs well while giving materially better recall than a 256/512 truncation. HNSW over ivfflat specifically because ivfflat's `lists` parameter must be tuned against table size — meaningless for a table that starts at zero rows and grows from there; HNSW has no such training-data dependency. This choice is explicitly provisional, carried forward as an open question exactly like Phase 0 → Phase 1's own embedding-model question was.

## What this phase's research does NOT yet resolve

- **Full Bayesian contradiction resolution** (the math-spec's literal Phase 1 assignment) is deliberately not attempted this phase — see ADR 0008 and `docs/math-spec/phase1-math-spec.md`. There is no retrieval-outcome feedback loop yet to calibrate a real posterior against, the same objection Phase 0's math-spec raised against attempting salience/decay/ranking prematurely. A minimal deterministic rule ships instead; the real math is Phase 2's problem, once consolidation gives the system something to learn from.
- **Sophisticated entity resolution** (coreference, nicknames, fuzzy matching) is out of scope. Phase 1 uses exact normalized-name matching within `(namespace, entity_type)`. This is a known, named simplification, not an oversight — full entity resolution is a deep sub-problem (see the Research Report's competitor analysis of extraction fidelity trade-offs) deserving its own future research pass once real extracted data shows how often naive matching actually misfires.
- **The extraction-fidelity trade-off** Phase 0's memo flagged (Haiku bulk extraction vs. Sonnet for ambiguous cases) is resolved minimally: Haiku-tier for all Phase 1 extraction (structured JSON via tool-calling), with the harder ambiguous-case routing left as an open question — Phase 1's exit criterion doesn't require resolving genuinely ambiguous extractions, only a clean-cut contradiction.
- **Zep/Graphiti** are the closest prior-art reference for bi-temporal graph modeling among the competitors Phase 0's memo already named (Mem0, Letta, Zep, MemOS, Cognee, MIRIX) — Zep/Graphiti specifically publishes its bi-temporal edge model (`valid_from`/`valid_to`/`invalid_at`) as a point of comparison. This phase's `relations` schema (see the plan's schema sketch) borrows the same valid-time/transaction-time split, adapted to Postgres tables rather than their dedicated graph backend.

## Open questions carried forward to Phase 2's research memo

- Whether `voyage-4`/1024/HNSW remains the right choice once real retrieval-quality data exists from actual usage.
- Whether the ArcadeDB spike's findings (cold-start latency, real install friction, actual Windows wheel behavior for this Python/OS combination) change the graph-store calculus once traversal patterns beyond 2-3 hops are needed — the concrete trigger ADR 0006 names.
- The real confidence-weighted Bayesian contradiction-resolution math, once consolidation gives the system retrieval-outcome feedback to calibrate against.
- Whether the deterministic contradiction rule's behavior in practice (most-recent-wins above a confidence floor, else flagged contested) produces enough contested cases to matter, or whether the floor needs tuning.
